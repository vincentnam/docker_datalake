# Keycloak ↔ Keystone OIDC federation

This folder wires an OpenID Connect federation between **Keycloak** (identity
provider) and **Keystone** (OpenStack identity service). Everything is driven
from the root [`conf.env`](../../conf.env); the per-service config files are
generated by `create_conf.sh` and `create_docker.sh`.

## What gets configured

| Piece | Where | Generated by |
|-------|-------|--------------|
| Keycloak container | `docker-compose_datalake.yml` (`keycloak` service) | `create_docker.sh` (only when `DEPLOY_KEYCLOAK=true`) |
| Realm import (`datalake` realm, `keystone` client, sample user/group) | `rawdata_zone/openstackKeycloak/realm/datalake-realm.json` | `create_conf.sh` |
| Apache `mod_auth_openidc` (OIDC relying party) | `/etc/apache2/conf-available/keystone-oidc.conf` inside the Keystone container | `scripts/init-keystone.sh` at startup |
| Keystone `[auth]`/`[federation]` sections | `rawdata_zone/openstackKeystone/conf/etc/keystone/keystone.conf` | static |
| Identity provider + mapping + protocol | Keystone DB | `scripts/bootstrap_keystone.sh` |
| `mod_auth_openidc` Apache module | Keystone LOCI image | `rawdata_zone/openstackKeystone/build.sh` (`libapache2-mod-auth-openidc`) |

## Configuration (conf.env → `KEYCLOAK / KEYSTONE FEDERATION CONF`)

| Variable | Meaning |
|----------|---------|
| `FEDERATION_ENABLED` | Master switch. `false` keeps Keystone in pure password mode. |
| `DEPLOY_KEYCLOAK` | `true` = run the bundled Keycloak container; `false` = reuse an external one. |
| `KEYCLOAK_URL` | Public base URL of Keycloak (no trailing slash, no `/realms`). |
| `KEYCLOAK_REALM` | Realm holding the datalake users. |
| `KEYCLOAK_CLIENT_ID` / `KEYCLOAK_CLIENT_SECRET` | OIDC confidential client used by Keystone. |
| `KEYCLOAK_ISSUER` | Leave empty to derive `${KEYCLOAK_URL}/realms/${KEYCLOAK_REALM}`. Set it for legacy `/auth/realms/...` Keycloak. |
| `KEYCLOAK_ADMIN` / `KEYCLOAK_ADMIN_PASSWORD` | Admin console credentials of the **bundled** Keycloak. |
| `KEYCLOAK_HOST_PORT` | Host port exposed for the bundled Keycloak (default `8088`). |
| `OIDC_CRYPTO_PASSPHRASE` | Secret used by `mod_auth_openidc` to encrypt its session state. |
| `KEYCLOAK_IDP_ID` / `KEYCLOAK_PROTOCOL_ID` | Keystone identity-provider id / protocol id (`keycloak` / `openid`). |
| `KEYSTONE_PUBLIC_URL` | Browser-facing Keystone URL, used to build the OIDC redirect URI. |
| `FEDERATED_DOMAIN` / `FEDERATED_GROUP` / `FEDERATED_PROJECT` / `FEDERATED_ROLE` | Keystone target the Keycloak users are mapped onto. |
| `KEYCLOAK_SAMPLE_USER` / `KEYCLOAK_SAMPLE_PASSWORD` | Demo user pre-created in the bundled realm. |

## Using an existing / external Keycloak

Set in `conf.env`:

```ini
DEPLOY_KEYCLOAK="false"
KEYCLOAK_URL="https://sso.example.com"        # or https://sso.example.com/auth for legacy
KEYCLOAK_REALM="my-realm"
KEYCLOAK_CLIENT_ID="keystone"
KEYCLOAK_CLIENT_SECRET="<secret from your Keycloak>"
# KEYCLOAK_ISSUER=""  # leave empty unless your realm lives under /auth/realms/<realm>
```

No `keycloak` container is generated and no realm is imported. On the external
Keycloak you must create, in `my-realm`, a confidential client matching
`KEYCLOAK_CLIENT_ID`/`SECRET` with:

* **Standard flow** + **Direct access grants** enabled,
* a valid redirect URI of `${KEYSTONE_PUBLIC_URL}/*`,
* a *group membership* mapper exposing a `groups` claim (optional — only if you
  want to drive Keystone groups from Keycloak groups; see `mapping_rules` note
  below).

Everything else (IdP/mapping/protocol registration, Apache OIDC config) is
identical to the bundled case.

## Web GUI login (username/password + Keycloak SSO)

The web GUI offers **two** login paths, both ending with a *Keystone* token
stored as Bearer (so the rest of the app is unchanged):

1. **Username / password** — unchanged, authenticates directly against Keystone
   (`v3password`). For local Keystone accounts.
2. **"Se connecter avec Keycloak" (SSO)** — OIDC Authorization Code, handled by
   Flask as a **Backend-for-Frontend** so the client secret never reaches the
   browser:

   ```
   [SSO button] → GET /api/auth/login  → redirect to Keycloak (browser)
                → Keycloak login page (KEYCLOAK_PUBLIC_URL)
                → GET /api/auth/callback?code=…  (Flask)
                     · keystoneauth v3oidcauthcode : code → federated Keystone token
                     · scope to FEDERATED_PROJECT
                → redirect to WEB_GUI_URL/#sso_token=…&project=…
                → GUI stores the token and lands on /buckets
   ```

   If a valid token is already present, the login screen is skipped. SSO errors
   are returned to the GUI as `#sso_error=…`.

Keystone validates the Keycloak **access token** as an OAuth2 resource server
(`AuthType oauth20`, `OIDCOAuthVerifyJwksUri` → internal JWKS). The browser-only
WebSSO (Horizon code flow) is left commented in `keystone-oidc.conf`.

Flask reads (generated into its `.env` by `create_conf.sh`):
`KEYCLOAK_URL`, `KEYCLOAK_PUBLIC_URL`, `KEYCLOAK_REALM`, `KEYCLOAK_CLIENT_ID`,
`KEYCLOAK_CLIENT_SECRET`, `KEYCLOAK_REDIRECT_URI`, `KEYCLOAK_IDP_ID`,
`KEYCLOAK_PROTOCOL_ID`, `FEDERATED_PROJECT`, `WEB_GUI_URL`, `FLASK_SECRET`.

## ⚠️ Internal vs external URL (the classic federation gotcha)

The OIDC **issuer** advertised by Keycloak must match the `iss` claim in the
tokens *and* be reachable by every party. There are two consumers with
different network views:

* **Keystone / Flask** (inside the `swift-cluster` docker network) reach
  Keycloak by its service name → `KEYCLOAK_URL="http://keycloak:8080"`.
* **The end-user browser** reaches Keycloak by a host-reachable URL →
  `KEYCLOAK_PUBLIC_URL="http://localhost:8088"`.

This is why there are **two** URL variables. The bundled Keycloak is pinned to
the public one (`KC_HOSTNAME=$KEYCLOAK_PUBLIC_URL`) so the token **issuer** is
always `${KEYCLOAK_PUBLIC_URL}/realms/<realm>` regardless of which URL was used,
while `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true` lets in-cluster services keep using
`keycloak:8080` for the token/JWKS endpoints. Concretely:

* the Keystone IdP `remote-id` = the **public** issuer (matches the `iss` claim),
* Keystone validates token signatures via the **internal** JWKS URI,
* Flask exchanges the auth code on the **internal** token endpoint,
* the browser is sent to the **public** URL to log in.

With the defaults (bundled Keycloak on host port `8088`, GUI on `7000`) both the
**web GUI SSO** and the **server-to-server** flows work out of the box. For an
**external** Keycloak, set `KEYCLOAK_URL` and `KEYCLOAK_PUBLIC_URL` to the same
reachable URL.

> Browser **WebSSO through Horizon** (not the web GUI) additionally needs the
> commented `openid-connect` block in `keystone-oidc.conf` plus the
> `trusted_dashboard` / `sso_callback_template` lines in `keystone.conf`, and a
> Keycloak metadata URL reachable from the Keystone container.

## Smoke test (CLI, server-to-server)

After `./start.sh -br` (datalake profile), from a shell that can reach the
`swift-cluster` network (e.g. `docker compose exec keystone_bootstrap sh`):

```sh
openstack --os-auth-type v3oidcpassword \
  --os-auth-url http://keystone:5000/v3 \
  --os-identity-provider keycloak \
  --os-protocol openid \
  --os-client-id keystone \
  --os-client-secret <KEYCLOAK_CLIENT_SECRET> \
  --os-openid-scope "openid profile email" \
  --os-discovery-endpoint http://keycloak:8080/realms/datalake/.well-known/openid-configuration \
  --os-username datalake-user \
  --os-password <KEYCLOAK_SAMPLE_PASSWORD> \
  token issue
```

A token scoped to the `federated` project (member role) confirms the
federation is working end to end.

## Notes on the mapping rules

`scripts/bootstrap_keystone.sh` renders the Keystone mapping so that every
Keycloak user **member of the `FEDERATED_GROUP` Keycloak group** becomes an
ephemeral Keystone user (in the `FEDERATED_DOMAIN` domain) with their own
auto-provisioned project (named after the username) and `FEDERATED_ROLE` on it.

The group is the **datalake access gate** :

* not in the group → authenticated by Keycloak but refused by Keystone
  (the mapping rule requires the `groups` claim to contain `FEDERATED_GROUP`) ;
* removed from the group → refused at the **next** login (the current token
  lives until expiry) ; the shadow user, project and data are kept, and
  recovered as-is if the user is added back.

This requires the `groups` protocol mapper on the Keycloak client (present in
the bundled realm ; on an external Keycloak create it manually : client scopes
→ `keystone-dedicated` → Add mapper → Group Membership, claim `groups`, full
path off). The Apache config pins `OIDCClaimDelimiter ";"` so multi-valued
claims match Keystone's assertion splitting.
